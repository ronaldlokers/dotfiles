# Zen Preferences Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Write twenty-two deliberate Zen Browser preferences from this repo into the browser's profile on every machine, so a rebuilt machine needs no manual `about:config` work.

**Architecture:** A `run_after` chezmoi script resolves the active Zen profile directory (whose name is random per machine) and writes a `user.js` into it, rendered from a single `.chezmoitemplates` file that holds the preference list. Zen reads `user.js` at every startup, so the listed preferences become repo-owned. Nothing else in the profile is touched.

**Tech Stack:** POSIX `sh` (chezmoi script templates), chezmoi templates, `bats` for tests, `shellcheck` + `actionlint` via `mise run lint`.

**Spec:** `docs/superpowers/specs/2026-08-31-zen-prefs-design.md`

## Global Constraints

- Target shell is POSIX `sh`, not bash. The script runs under `set -eu`.
- Scripts under test are not executable in the source tree. Invoke them through `sh` in tests, never directly.
- The script is `run_after`, never `run_onchange`. A `run_onchange` records its hash on a skipped run, which would permanently mark the seeding done on a machine that had no Zen yet.
- The script must exit 0 and write nothing inside a container (gate on the shared `is-container` template) and where `zen-browser` is not on `PATH`.
- The script must never write `installs.ini` or `profiles.ini` when a profile already exists, and must never touch any profile content other than `user.js`.
- Profile resolution order is `installs.ini` → `profiles.ini` `[InstallXXXX]` → `profiles.ini` `[ProfileN] Default=1` → create. Order 3 must never be consulted before orders 1 and 2.
- Paths in both ini files are relative to `${XDG_CONFIG_HOME:-$HOME/.config}/zen` when `IsRelative=1`, absolute otherwise.
- Twenty-two preferences are managed. The exact list and values are in the spec's table and are reproduced verbatim in Task 2.
- Tests run against a fake `$HOME` under `$BATS_TEST_TMPDIR`, never the real Zen profile.
- Every test must be observed failing against the code it covers before the implementation lands, and the observed assertion-failure text recorded in the commit or PR body. A "command not found" or missing-file error is not proof; the failure must be an assertion in code that runs.
- Templates are rendered in tests with the existing `render_template` helper from `tests/helpers.bash`, which clears the `XDG_*` variables. Do not call `chezmoi execute-template` directly.

```bash
# Writes a fake zen-browser into $1 (a directory placed first on PATH). The
# seed script only needs zen-browser to exist for its `command -v` gate; the
# -CreateProfile form is implemented so the creation branch can be driven
# without a real browser or a display.
#
#   ZEN_LOG        file to record every invocation's argv, one per line
#   ZEN_CREATE_RC  exit code for -CreateProfile            (default 0)
make_zen_browser_stub() {
	local bin="$1"
	mkdir -p "$bin"
	cat >"$bin/zen-browser" <<'STUB'
#!/bin/sh
[ -n "${ZEN_LOG:-}" ] && printf '%s\n' "$*" >>"$ZEN_LOG"
# Zen takes the profile name and its directory as one argument, space
# separated: -CreateProfile "<name> <path>". Creating the directory and
# registering it in profiles.ini is what the real binary does.
if [ "${1:-}" = "-CreateProfile" ]; then
	name="${2%% *}"
	path="${2#* }"
	rc="${ZEN_CREATE_RC:-0}"
	[ "$rc" -ne 0 ] && exit "$rc"
	mkdir -p "$path"
	zen_dir="${XDG_CONFIG_HOME:-$HOME/.config}/zen"
	mkdir -p "$zen_dir"
	{
		printf '[Profile0]\n'
		printf 'Name=%s\n' "$name"
		printf 'IsRelative=0\n'
		printf 'Path=%s\n' "$path"
		printf 'Default=1\n'
	} >>"$zen_dir/profiles.ini"
	exit 0
fi
exit 0
STUB
	chmod 755 "$bin/zen-browser"
}
```

```bash
#!/usr/bin/env bats
#
# run_after_24-seed-zen-prefs.sh.tmpl writes this repo's Zen preferences into
# the browser's profile as user.js.
#
# user.js cannot be an ordinary managed file: its path contains a randomly
# generated profile directory name, different on every machine, so chezmoi has
# no static target to map it to. The script resolves the profile and writes
# there.
#
# The resolution order is the part that matters and the part these tests exist
# to pin. profiles.ini's `Default=1` is NOT authoritative -- on the machine
# this was written for it marks an unused 4 KB profile while installs.ini
# names the 277 MB one holding the real session. A reader that trusts
# `Default=1` writes into the wrong profile and silently achieves nothing.

bats_require_minimum_version 1.5.0

setup() {
	load 'helpers'
	TMPL="$BATS_TEST_DIRNAME/../home/.chezmoiscripts/run_after_24-seed-zen-prefs.sh.tmpl"
	HOME="$BATS_TEST_TMPDIR/home"
	ZEN="$HOME/.config/zen"
	mkdir -p "$ZEN"

	BIN="$BATS_TEST_TMPDIR/bin"
	make_zen_browser_stub "$BIN"
	ZEN_LOG="$BATS_TEST_TMPDIR/zen.log"

	SCRIPT="$BATS_TEST_TMPDIR/seed.sh"
	render_template "$TMPL" "$SCRIPT" "$PATH"
	export HOME ZEN_LOG
}

run_seed() {
	run env -u XDG_CONFIG_HOME HOME="$HOME" ZEN_LOG="$ZEN_LOG" \
		PATH="$BIN:$PATH" sh "$SCRIPT"
}

# real machine has.
write_installs() {
	mkdir -p "$ZEN/$1"
	cat >"$ZEN/installs.ini" <<-EOF
		[15B76BAA26BA15E7]
		Default=$1
		Locked=1
	EOF
}
```

```sh
#!/bin/sh
# Write this repo's Zen Browser preferences into the browser's profile.
#
# user.js cannot be an ordinary managed file: its path contains a randomly
# generated profile directory name, different on every machine, so chezmoi has
# no static target to map it to. The list lives in .chezmoitemplates/zen-user-js
# and this script renders it into whichever profile it resolves.
#
# The preferences listed there are repo-owned. Zen re-reads user.js at every
# startup and its values override prefs.js, so changing one in the browser UI
# appears to work and reverts at the next restart. That is the trade accepted
# in docs/design-notes.md: reproducible on a new machine, not editable in place.
#
# A plain `run_after`, not a `run_onchange`, for the reason the enable scripts
# next door are: chezmoi records a run_onchange script's hash the moment it
# exits 0, including the exit 0 that means "nothing here to act on". A machine
# whose Zen has never been launched has no profile yet, and that exit 0 would
# have marked the seeding done for the life of the machine.
set -eu

# A container has no Zen and no display to run one on. Rendered into a variable
# rather than wrapping the body in a template `if`, the way the scripts next
# door do it: CI shellchecks the template, not the rendered script, and a bare
# template action at statement level does not parse as shell.
# shellcheck disable=SC1083
is_container={{ includeTemplate "is-container" . }}
# shellcheck disable=SC2154
if [ "$is_container" = "true" ]; then
	exit 0
fi

# No browser, nothing to configure. Not an error: this runs on every machine,
# and the package install is a later script's job.
command -v zen-browser >/dev/null 2>&1 || exit 0

zen_dir="${XDG_CONFIG_HOME:-$HOME/.config}/zen"

# Turns a Path= value into an absolute directory. IsRelative=1 means relative
# to the zen directory; anything starting with / is already absolute.
abs_profile() {
	case "$1" in
	/*) printf '%s\n' "$1" ;;
	*) printf '%s\n' "$zen_dir/$1" ;;
	esac
}

# Sets $profile_dir, or leaves it empty when no profile exists yet.
#
# installs.ini first, and this ordering is the whole reason the script exists.
# profiles.ini's `Default=1` is not what Zen honours -- on the machine this was
# written for it marks an unused 4 KB profile, while installs.ini names the one
# holding the actual session. A glob, or a reader that trusts `Default=1`,
# writes user.js into the wrong profile and silently achieves nothing.
resolve_profile() {
	profile_dir=""
	rel=""

	if [ -f "$zen_dir/installs.ini" ]; then
		rel="$(awk '/^Default=/ { print substr($0, 9); exit }' \
			"$zen_dir/installs.ini")"
	fi

	if [ -n "$rel" ]; then
		profile_dir="$(abs_profile "$rel")"
	fi
}

resolve_profile
[ -n "$profile_dir" ] || exit 0
[ -d "$profile_dir" ] || exit 0

target="$profile_dir/user.js"
tmp="$target.tmp.$$"

# The quoted heredoc delimiter stops the shell touching the content; chezmoi
# has already rendered the template by the time this runs.
# shellcheck disable=SC1083
cat >"$tmp" <<'ZEN_USER_JS'
{{ includeTemplate "zen-user-js" . }}
ZEN_USER_JS

if [ -f "$target" ] && cmp -s "$tmp" "$target"; then
	rm -f "$tmp"
	exit 0
fi

mv "$tmp" "$target"
echo "[zen] wrote user.js into $(basename "$profile_dir")"
```

```sh
resolve_profile() {
	profile_dir=""
	rel=""

	# 1. installs.ini: what Zen itself honours, per install.
	if [ -f "$zen_dir/installs.ini" ]; then
		rel="$(awk '/^Default=/ { print substr($0, 9); exit }' \
			"$zen_dir/installs.ini")"
	fi

	# 2. The same record mirrored into profiles.ini as an [InstallXXXX]
	#    section. Present on machines whose installs.ini has not been
	#    written yet.
	if [ -z "$rel" ] && [ -f "$zen_dir/profiles.ini" ]; then
		rel="$(awk '
			/^\[Install/ { in_install = 1; next }
			/^\[/        { in_install = 0 }
			in_install && /^Default=/ { print substr($0, 9); exit }
		' "$zen_dir/profiles.ini")"
	fi

	# 3. Last, and only last: the [ProfileN] section flagged Default=1. On a
	#    machine with more than one profile this is frequently not the one in
	#    use, which is why the two install records are consulted first.
	if [ -z "$rel" ] && [ -f "$zen_dir/profiles.ini" ]; then
		rel="$(awk '
			/^\[Profile/ { path = ""; isdef = 0; in_prof = 1; next }
			/^\[/        { in_prof = 0 }
			in_prof && /^Path=/      { path = substr($0, 6) }
			in_prof && /^Default=1/  { isdef = 1 }
			in_prof && isdef && path != "" { print path; exit }
		' "$zen_dir/profiles.ini")"
	fi

	if [ -n "$rel" ]; then
		profile_dir="$(abs_profile "$rel")"
	fi
}
```
